## What every other signal said
| Signal | Said |
|---|---|
| Kubernetes Job status | **Succeeded** |
| Exit code | **0** |
| Job log | **"settlement complete"** |
| `SettlementJobFailed` | inactive |
| `SettlementStale` | inactive (until 15 min later) |
| Pushgateway | metrics pushed fine |

Nothing was red. Compare INC-0001 through 0004 — all loud. This is the one every
payments company has a story about.

## What caught it
`settlement_records_processed == 0` for 1 minute. One rule. Without it the detection
path is: finance notices missing money movement → days later.

## Cause
Settlement produced zero records (simulated: `SETTLEMENT_FAIL_MODE=silent`). In real
life: an upstream feed was empty, a date filter excluded everything, a permission
silently returned no rows.

## The real fix — engineer it away
The alert is a backstop. **The job itself should refuse to report success on zero
records.** Ran it with `SETTLEMENT_STRICT=true`: exit 2, Job **Failed**, log line names
`reason=zero_records`. Now Kubernetes, the log, `SettlementJobFailed`, *and*
`SettlementZeroRecords` all agree — four signals instead of one.

This is the difference between fixing an incident and engineering it away, and it is
exactly what the job description means by "engineer permanent solutions."

## Follow-up
- [ ] Make `SETTLEMENT_STRICT=true` the default in `k8s/settlement.yaml`
- [ ] Add a plausibility bound: fewer than 1,000 records is also suspicious, not just zero
- [ ] Every "expected every N minutes" job in the company needs a `…Stale` alert — list them
