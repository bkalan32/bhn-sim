# INC-0015 — Untracked infrastructure change: settlement's metrics silently stopped (Day 13)

Nothing crashed. No alert fired. A colleague "hot-fixed" the pushgateway release by hand
(`helm upgrade --set serviceMonitor.enabled=false --reuse-values`, pinned to the running chart
version), Prometheus dropped the scrape target within a minute, and every settlement panel
went blank — including the one alert that watches settlement freshness, `SettlementStale`,
whose expression `time() - settlement_last_success_timestamp > 900` is **empty** when the
metric does not exist and therefore cannot fire, however stale settlement gets. The incident
was declared by a human, because that is the only way this class gets opened.

**Root cause category:** untracked infrastructure change. **Permanent fix:** the nightly
drift check (Jenkins `infra-drift-check`, `terraform plan -detailed-exitcode`, exit 2 = red).

## Two clocks (CORRECTIONS D4)
There is no alert on this incident, so *alert → resolved* is undefined. The record keeps
**declared → repaired = 51.1 min** (the human clock) and **injected → detected ≈ 5 min**
(the platform clock, once the platform could see it). The nightly job's own proof run:
build #1 clean → SUCCESS, drift re-injected → build #2 **FAILURE** with the ServiceMonitor
line in the console, `terraform apply` → build #3 SUCCESS.

## What happened *during* the incident — a real one, on the same ticket
At 01:58:57Z, while kps was mid-upgrade and the WSL VM was under memory pressure (Prometheus,
kube-state-metrics, the operator and Grafana all restarted in that window), the settlement
CronJob's run **failed** — a real `SettlementJobFailed`, which *could* fire because it reads
Job status from kube-state-metrics, not from the pushgateway. It landed on this open ticket
(same service). The remediator's tier-1 signature took it: `rerun_settlement` at 01:59:53Z,
Job `settlement-remediator-1788919157` Complete, **4 445 records**, alert resolved 02:08:57Z.
Nobody touched kubectl. Day 12's automation handled a genuine fault inside Day 13's drill, and
the ticket shows both, in order.

## Why this is the argument for IaC in one record
Application changes have been tracked since Day 6: the pipeline records every deploy with a
change-cause and an annotation, and the bot's enrichment reads them. Infrastructure changes
— a chart value, a version bump, a namespace label — were the untracked class, and they
produce the confusing incidents: no crash, no alert, a metric just stops. Terraform's plan is
the diff between "what we said" and "what is". The nightly job turns that diff into a red
build, which is an alert like any other. And the day's own finding: the diff only exists if
the tool is configured to compute it (B8), and only means anything if the render is
deterministic and free of secrets (B9, B10). "We have Terraform" is not the same as "we
would see this".

## What the copilot said (Eval 5)
Asked *"Is settlement healthy right now? When did it last succeed and how many records?
Answer only from tools."* It queried Prometheus (all empty), then went to `kubectl get jobs`
and the newest Job's logs, and answered from there: *last successful run 01:25:09Z, 5 941
records, last three Jobs Complete* — every claim cited to a tool — and added: *"Settlement
metrics … are not available in Prometheus (query_prometheus: all returned empty)."*
**Pass**: it did not invent a number, it found an independent source, and it disclosed the
gap. One level short of the insight: a human would have said "settlement is fine **and**
your monitoring of it is broken" — the second half *is* the incident. It reported the gap as
a footnote, not a finding. (8 tool calls, 17.9 s, ≈$0.02.)

## Related, same day: the Fluent Bit restarts (silent, unticketed)
Found while reading the import's output: `fluent-bit` at **10 restarts**, all exit 0, one
every ~40 min for 5 h — the chart's default 1 s probe timeout against an HTTP server that
shares its event loop with the HEC output; the kubelet read "slow" as "dead". No alert, no
ticket, log shipping paused for seconds each time. Fixed as the second change through
Terraform (`livenessProbe.timeoutSeconds: 5`, commit `bc155a4`). **Verification:** the
replacement pod at 0 restarts after 76 min, against a prior rate of one per ~40 min.
Carry to Day 14's review as the silent-incident example: the platform layer had a fault
for hours that nothing recorded until a human read a pod list.
