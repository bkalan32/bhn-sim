# INC-0013 — Tier-1 drill: settlement crash, re-run by automation (Day 12)

`SETTLEMENT_FAIL_MODE=crash`, one job run: it crashed, `SettlementJobFailed` fired, the ticket
opened, and the remediator created a new Job from the CronJob. That job crashed too — the mode
was still `crash` — and the remediator wrote an honest **FAILED** note and started a bounded
retry clock. The cause was fixed (mode `none`) while the clock ran; the retry succeeded and
`settlement_last_success_timestamp` recovered with nobody touching kubectl.

## A genuine self-heal, witnessed end to end — with an honest asterisk
The shape is exactly the policy's: first attempt reported a **failure**, not a success; a
bounded retry was scheduled and announced; the cause was fixed by a human in the window;
the retry succeeded and `last_success` recovered with nobody running `kubectl create job`.

The asterisk: the first failure was the *tool's*, not the job's. The drill intended "the
re-run crashes too because the mode is still `crash`", and the CronJob's own tick at 21:25 did
exactly that — but the remediator's re-run never started, because kubectl spent its first 30
seconds discovering the API. Two things follow. The failure note was still *true* ("could not
create job … timeout"), which is the point of reporting outcomes rather than attempts. And
the fix is in the remediator, not the policy: discovery is warmed at startup and `create`
gets 120 s (0.1.3). Re-running this drill on 0.1.3 should produce the intended
*"job Failed — settlement crashed fail_mode=crash"* first note.
