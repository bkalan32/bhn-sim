## Impact

100% of card activations failing for approximately _N_ minutes. Every request also took
3+ seconds before failing, so point-of-sale terminals hung before showing the decline.
In production this is checkout lines stopping in every store.

## Detection

The alert fired _N_ minutes after the fault was injected. Detection latency is the
`[2m]` rate window plus `for: 2m`, so roughly 2–4 minutes by design.

_Was that fast enough? Note your answer — it is an alert-tuning decision, not a given._

## Diagnosis path

1. **Alert** said *errors* — `ActivationHighErrorRate`, severity critical
2. **Grafana** said *everything, and slow* — error rate to 100%, p95 past 3s
3. **Splunk** said *which dependency*:
   ```spl
   index=main app.service=activation app.status=error earliest=-5m | stats count by app.reason
   ```
   → `fraud_service_timeout`

That three-step narrowing — is something wrong / what shape / what exactly — is the
whole job. Metrics find it, logs explain it.

## Cause

Fraud check dependency unavailable (simulated with `FRAUD_SVC_DOWN=true`). The
activation service waits the full 3-second timeout on every request before failing.

## Fix

```bash
kubectl set env deployment/activation -n payments FRAUD_SVC_DOWN=false
```

## Follow-up — the part that actually matters

**Should activation fail fast when fraud is down, instead of waiting 3 seconds?**

Right now one dead dependency costs every caller 3 seconds before returning an error
they were always going to get. A circuit breaker would fail in milliseconds once it saw
the dependency was down, which keeps POS terminals responsive and stops the thread pool
filling with doomed requests.

Deeper question: **must** a fraud check block activation at all, or could low-value
activations proceed and be checked asynchronously? That is a business decision, not an
engineering one — but engineering is what surfaces it.

This bullet is the difference between fixing an incident and engineering it away.
