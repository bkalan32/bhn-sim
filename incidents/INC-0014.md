## The timeline reads like a story
alert → proposal → human approval → action → recovery. Every step on one record, with times,
written by the automation itself. During a bridge, "what has the automation already done?"
has an instant answer.

## Approve-to-recover, next to the benchmarks
| Path | What recovers production | alert → recovered | human effort |
|---|---|---|---|
| Day 6, manual | a human runs `rollout undo` after reading the dashboard | _from INC-0006 / 54-manual-rollback.sh_ | find the cause, type the command |
| Day 6/10, pipeline Verify | the pipeline's post-deploy check + auto-rollback | ≈ 2 min wait + ~30 s rollback, **before** any alert | none — but only for releases that go through the pipeline |
| **Day 12, tier 2** | proposal + one human yes | **_N_ s** (approve → recovered _N_ s) | read one note, run one command |

The honest comparison: the pipeline path is faster *for deploys*, because it does not wait for
an alert. The tier-2 path covers what the pipeline cannot — a bad release that slipped past
Verify, a config change, a rollback needed an hour later — and it turns "find the cause, then
decide, then type" into "decide".
